### Detalle (medio/alto/crítico)

#### A-001 — Webhooks Green API incompatibles con middleware HMAC

- **Evidencia:**
  - `ProvisionGreenInstanceJob` L68–73 configura `webhookUrlToken` → `WEBHOOK_SECRET`
  - `VerifyWebhookSignature` L19–28 valida `X-Webhook-Signature` (HMAC SHA-256 del body)
  - `WebhookIdempotency` exige `X-Event-Id`
  - [Green API docs](https://greenapi.com/en/docs/api/receiving/technology-webhook-endpoint/): envía `Authorization: Bearer <token>`, sin headers custom
  - Tests (`WebhookVerificationTest`) solo cubren esquema HMAC interno
- **Impacto:** instancias pueden permanecer en `waiting_qr` tras escanear QR; flujo demo→pago incompleto en ops reales
- **Recomendación humana:** adapter dual (Bearer + idempotencia por payload Green) antes de confiar en webhooks en VPS

#### A-002 — Coordinación deploy activate-plan

- **Evidencia:** PR #14–#15 en api; Framework commit `2c71d3f` (2026-07-15) mergeó `feature/backoffice-api-integration` con `activatePlan()` y hardening membership
- **Impacto:** error SQL/runtime si `meta` no existe; activaciones fallan en cadena
- **Recomendación humana:** checklist en `docs/superpowers/plans/2026-07-14-plan-activation-closure.md`

#### A-003 — PATCH tenants bypass de activate-plan

- **Evidencia:**
  - `UpdateTenantRequest` L22–27 acepta `commercialStatus`, `planSlug`, `messagesMonthlyLimit` sin `Rule::in` catálogo
  - `ActivatePlanService` revoca tokens y sincroniza permisos; PATCH no
- **Impacto:** token platform + `tenants.gestionar` puede elevar plan/límites sin auditoría `meta` ni rotación Sanctum
- **Recomendación:** restringir PATCH a campos no comerciales o reutilizar `ActivatePlanService`
